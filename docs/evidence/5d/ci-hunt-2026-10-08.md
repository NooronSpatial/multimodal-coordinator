# The CI hunt (2026-10-08) — why PR 63's check went red

*What this is:* the hunt for the red check on PR 63 (milestone 5d), from the
runner's own logs to a cause reproduced on this Mac, fixed red-first, and
measured again. Every run is one line in
[`ci-hunt-2026-10-08-runs.txt`](ci-hunt-2026-10-08-runs.txt); the script that
reads the CI logs is [`ci-hunt-2026-10-08-timeline.py`](ci-hunt-2026-10-08-timeline.py).

## The picture

```
 THE BENCH'S SERVER, STOPPED TWICE (one row since 5a: "the network, unplugged", then teardown)

             first stop()                         second stop()
 5a … 5c:    close(socket)                        close(socket) AGAIN — a number the system
                                                  may have given to another test (fast, silent)
 5d (§233):  poke · WAIT for the accept thread ·  WAIT again — the thread has already ended, so
             close(socket)                        the wait runs its whole 5 s cap, holding a
                                                  thread of Swift's pool — then close(socket) AGAIN

 CI's runner has 3 cores, so Swift's pool has 3 threads. One of them held for 5 s,
 in the busiest seconds of the suite, and the real-audio rows ran out of their 3 s drain.
```

## What CI showed

- Before 5d, about 40 runs were green. On this branch, 6 of 16 runs went red with
  the same rows: the real-audio strand rows (`PlaybackLeadStrandTests`, D-141),
  once with the step-record margin row beside them. A seventh red run was a lint slip.
- The strand rows' own durations (measured by the test library itself, so not
  affected by how the log is written) grew on this branch. THE HOLE took
  0.7–2.7 s before 5d and 0.6–6.1 s on this branch, and it failed at 5.9–6.1 s.

**A wrong first reading, corrected.** I first read the log as "the whole test
process freezes for 2 to 8 seconds" and wrote that in the PR. That came from the
log's timestamps. They arrive in batches: one row took 0.9 s by its own clock,
yet its "started" and "passed" lines carry the same timestamp. The timestamps
cannot show a freeze, and the durations alone do not prove one.

## Reproduced on this Mac

On ten cores, the rows never fail, even with fourteen CPU burners running beside
them (E1, E2: 10 of 10 and 10 of 10). CI differs in the size of Swift's pool,
which is one thread per core. `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` holds the pool to
ONE thread, so it is harsher than CI's three, but it is the same kind of
pressure. The 4y hammer is skipped, as CI's suite step skips it (D-111).

| one-thread pool, six runs each | THE CONTRAST | red runs |
|---|---|---|
| main (`f11dca4`, before 5d) | 0.5–1.2 s | **0 of 6** |
| this branch (`115c30d`) | 1.0 s, or 5–6 s | **4 of 6** (3 THE CONTRAST, 1 a download row) |
| this branch without the barge rows that spin 2 s | 1.0 s, or 5–6 s | **2 of 6**, so those rows are not the cause |

Each run on this branch had one quiet stretch of almost exactly 5 s, when no
test started or ended (a pseudo-terminal made the output arrive line by line, so
these timestamps are real). In all three timestamped runs, that stretch is
exactly the span of one row: `MLXBackgroundInstallTests` "expectedInstall makes
one request…" (run 1: 23.819 → 28.928 s; run 2: 8.996 → 14.149 s; run 3:
8.455 → 13.572 s, and THE CONTRAST, started at 8.390 s, ended at 13.572 s with
it). Alone, the row took 5.016, 5.022 and 5.014 s. Run 3 is kept:
[`ci-hunt-2026-10-08-strict-stamped-the-5s-stretch.log`](ci-hunt-2026-10-08-strict-stamped-the-5s-stretch.log);
a failing one-thread run too:
[`ci-hunt-2026-10-08-strict-run3-FAILED.log`](ci-hunt-2026-10-08-strict-run3-FAILED.log).

## The cause and the fix

That row stops its server in the middle ("the network, unplugged"), and its
teardown stops it again. Since `e306520` (§233, kept by D-136's poke), `stop()`
waits up to 5 s for the accept thread; the thread signals once, so the second
`stop()` waits the whole cap. The second call has also closed the socket's
number again since 5a.

- RED (`df1e042`): two counters in the server; stop twice; each must be 1.
  Both were 2, and the row took 5.012 s
  ([`red-2026-10-08-l-a-second-stop.log`](red-2026-10-08-l-a-second-stop.log)).
- GREEN (`6568619`): `stop()` acts once; a second call returns at once.

| after the fix | |
|---|---|
| one-thread pool, ten runs | **10 of 10** pass; THE CONTRAST 0.97–1.07 s every run, as on main |
| the expectedInstall row | 5.0 s → 0.006 s |
| the whole suite, ten cores | 1 042 tests pass; strict lint clean |

## What is NOT proven

- **CI itself.** The fix is measured on a one-thread pool on this Mac. CI's
  three-thread pool is confirmed only by CI runs.
- **CONTROL's "played 0".** CI's last red run said the CONTROL row's player
  played 0 of 4 buffers in its 3 s drain. "Played" is counted by the audio
  engine's own callback, not by Swift's pool, so a held pool thread does not
  explain it directly. CONTROL starts in the first seconds, when about a thousand
  tests start at once, and it has always been close to its line on CI: 4.6–7.3 s
  before 5d, and it failed at 7.4 and 12.2 s on this branch. If it goes red
  again, its story will say more.
- **The old double close** (since 5a) closed a number the system may already
  have handed to another test. That fits the "descriptor closed under its owner"
  family that §233 hunted (D-135) and never explained. It is not proven to be
  that family.
- **One download row failed once** before the fix, on the one-thread pool
  ("two callers, one transfer": two requests where one was expected). It has not
  failed since. Not explained.
